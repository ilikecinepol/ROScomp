# Техническое задание ИИ-агенту: перенос решения Webots на реальный Unitree Go2 Pro

## Короткая постановка задачи

Нужно превратить текущее решение для Webots в ROS 2-приложение для реального **Unitree Go2 Pro** на судейском **Raspberry Pi 5 с Ubuntu 24.04 arm64 и ROS 2 Jazzy**. Приложение должно получать штатные данные лидара, камеры, IMU, одометрии и состояния робота, строить карту, принимать цель, планировать движение и подавать безопасные высокоуровневые команды скорости.

Главное архитектурное решение: **оставить SLAM, Nav2, веб-интерфейс и логику миссии над стандартным ROS-интерфейсом, а симуляционный UDP-мост исключить из реального launch-файла**. На реальном роботе ноги и устойчивую походку реализует штатная прошивка Unitree. Нельзя переносить на настоящего робота кинематический контроллер ног из Webots и нельзя подавать `LowCmd`.

До написания кода агент обязан снять фактический контракт интерфейсов с назначенного Pi. Нельзя угадывать тип `/robot_state`, имя Sport-сервиса, сигнал старта, QoS, `frame_id`, единицы, знаки осей или состав полей облака.

## Данный регламентом ROS-контракт

| Назначение | Топик | Тип | Ожидаемая частота | Что обязательно проверить на реальном Pi |
|---|---|---|---:|---|
| Облако 4D-лидара Go2 L1 | `/point_cloud2` | `sensor_msgs/msg/PointCloud2` | около 10 Гц | `frame_id`, поля `x/y/z`, дополнительные поля, endian, плотность, min/max высота, timestamp и QoS |
| 2D-проекция для Nav2 | `/scan` | `sensor_msgs/msg/LaserScan` | около 10 Гц | направление углов, `angle_increment`, `range_min/max`, `inf/nan`, видимость горок и низких объектов, QoS |
| Фронтальная камера | `/camera/image_raw` | `sensor_msgs/msg/Image` | около 15 Гц | `encoding`, разрешение, шаг, задержка, `frame_id` и QoS |
| Сжатая камера | обычно `/camera/image_raw/compressed` | `sensor_msgs/msg/CompressedImage` | проверить | точное имя и транспорт |
| Калибровка камеры | `/camera/camera_info` | `sensor_msgs/msg/CameraInfo` | проверить | матрицы `K/D/R/P`, distortion model, соответствие разрешению изображения |
| IMU | `/imu` | `sensor_msgs/msg/Imu` | около 100 Гц | ориентация, угловая скорость, ускорение, ковариации, знак pitch/roll/yaw и `frame_id` |
| Одометрия ног | `/odom` | `nav_msgs/msg/Odometry` | около 50 Гц | `header.frame_id`, `child_frame_id`, знак `x/y/yaw`, система координат twist, ковариации и дрейф |
| Состояние Go2 | `/robot_state` | тип SDK, узнать фактически | около 50 Гц | FSM, gait, высота корпуса, силы/контакты стоп, температуры, заряд, error flags |
| Геометрия | `/tf`, `/tf_static` | `tf2_msgs/msg/TFMessage` | — | связность `odom -> base_link -> lidar/camera/imu`, отсутствие двух издателей одного transform |
| Управление скоростью | `/cmd_vel` | `geometry_msgs/msg/Twist` | публиковать непрерывно | фактические знаки осей, задержка, работа watchdog |

Предельные значения регламента: `|vx| <= 1.5 м/с`, `|vy| <= 1.0 м/с`, `|wz| <= 2.0 рад/с`. Это верхние ограничения драйвера, а не стартовые скорости испытаний.

Робот также имеет датчики контакта стоп и батареи; ожидается, что они входят в `/robot_state`. Их точные поля и единицы надо получить командой `ros2 interface show` и из одного сообщения, затем внести в конфигурацию.

## Быстрая карта замены Webots на реального робота

| Сейчас в симуляции | На реальном Go2 |
|---|---|
| `go2_virtual_sport.py` двигает модель и суставы | штатная прошивка локомоции Unitree двигает ноги по high-level скорости |
| `cmd_vel_bridge.py` передаёт команды и датчики через UDP | судейский `go2_ros2_sdk` + WebRTC-bridge уже публикует ROS-топики и принимает `/cmd_vel` |
| Webots публикует `/scan`, `/camera/image_raw`, `/imu`, `/odom`, TF | эти же данные берутся из судейского ROS-драйвера; дополнительно доступен `/point_cloud2` и `/robot_state` |
| `slam_toolbox`, Nav2 и веб-интерфейс | сохраняются, но получают реальные данные и новые параметры калибровки/footprint/QoS |
| клик по карте | веб-узел отправляет `nav2_msgs/action/NavigateToPose` в `/navigate_to_pose` |
| Nav2 пишет прямо в `/cmd_vel` | Nav2 remap на `/cmd_vel_nav`, затем safety mux публикует итоговый `/cmd_vel` |

Внутренний контракт навигационного приложения:

| Интерфейс | Тип | Источник/получатель |
|---|---|---|
| `/map` | `nav_msgs/msg/OccupancyGrid` | `slam_toolbox` -> UI/Nav2 |
| `/navigate_to_pose` | `nav2_msgs/action/NavigateToPose` | UI/mission manager -> Nav2 |
| `/plan` и локальный план, точные имена проверить | `nav_msgs/msg/Path` | Nav2 -> диагностика/UI |
| `/cmd_vel_nav` | `geometry_msgs/msg/Twist` | Nav2 -> safety mux |
| `/cmd_vel_skill` | `geometry_msgs/msg/Twist` | obstacle skill -> safety mux |
| `/cmd_vel` | `geometry_msgs/msg/Twist` | safety mux -> судейский драйвер |

## Что агент должен определить на реальном Pi до реализации

Сделать read-only инвентаризацию и сохранить результат в `docs/real_interface_report.md` и `config/real_interface.yaml`:

```bash
source /opt/ros/jazzy/setup.bash
# Затем source судейского и командного overlay, пути узнать на Pi.
ros2 node list
ros2 topic list -t
ros2 service list -t
ros2 action list -t
ros2 param list
ros2 topic info -v /point_cloud2
ros2 topic info -v /scan
ros2 topic info -v /camera/image_raw
ros2 topic info -v /camera/camera_info
ros2 topic info -v /imu
ros2 topic info -v /odom
ros2 topic info -v /robot_state
ros2 topic echo /robot_state --once
ros2 topic echo /odom --once
ros2 topic echo /imu --once
ros2 topic hz /point_cloud2
ros2 topic hz /scan
ros2 topic hz /camera/image_raw
ros2 topic hz /imu
ros2 topic hz /odom
ros2 topic bw /point_cloud2
ros2 run tf2_tools view_frames
ros2 run tf2_ros tf2_echo odom base_link
ros2 run tf2_ros tf2_echo base_link lidar
```

Если имя рамы лидара отличается от `lidar`, использовать фактическое имя. Команды, которых нет в конкретной сборке Jazzy, заменить эквивалентной read-only диагностикой.

Отдельно найти и документировать:

1. точное имя, тип запроса и допустимые значения **Sport API**;
2. точный топик/сервис/поле **судейского сигнала старта**;
3. способ штатной остановки и подтверждение состояния стойки;
4. имя systemd-юнита драйвера и способ только чтения его статуса;
5. фактические QoS всех сенсорных потоков;
6. сетевой интерфейс, `ROS_DOMAIN_ID`, RMW и настройки DDS;
7. кто публикует `odom -> base_link`, а кто должен публиковать `map -> odom`;
8. доступен ли `/scan` сразу или его надо получать разрешённым `pointcloud_to_laserscan` из `/point_cloud2`.

Не останавливать судейский драйвер, не открывать собственное WebRTC-соединение и не отправлять команды движения во время этой стадии.

## Обязательная система координат

Внутренний интерфейс программы должен следовать ROS REP-103:

- `+x` — вперёд относительно корпуса;
- `+y` — влево;
- `+z` — вверх;
- `+angular.z` — поворот влево, против часовой стрелки при взгляде сверху;
- `base_link` — корпус, `odom` — локальная непрерывная одометрическая рама, `map` — рама SLAM.

Ранее в симуляции уже возникали ошибки со знаком движения и поворота. Поэтому нельзя добавлять `-1` или разворот на 180 градусов «на глаз». После read-only стадии провести отдельный тест осей с малыми импульсами и сравнить команду с `/odom`, IMU и видео:

1. `vx=+0.10`, остальные нули, 0.5 с — робот и `odom.x` должны идти вперёд;
2. `vy=+0.08`, остальные нули, 0.5 с — движение влево;
3. `wz=+0.15`, остальные нули, 0.5 с — поворот влево;
4. после каждого импульса отправить ноль и убедиться в остановке.

Эти значения являются начальными параметрами теста и должны лежать в YAML, а не быть зашиты в код.

## Требуемая архитектура ROS 2-пакетов

Создать отдельный overlay, например `real_go2_ws`, с пакетами или логически разделёнными узлами:

### 1. `go2_interface_check`

Read-only узел диагностики. Проверяет наличие, тип, частоту, возраст сообщений, QoS, frame IDs, связность TF и заполненность обязательных полей. Публикует `diagnostic_msgs/DiagnosticArray` и формирует машиночитаемый отчёт. Никогда не публикует `/cmd_vel`.

### 2. `go2_safety_cmd_mux`

Единственный узел команды, которому разрешено публиковать итоговый `/cmd_vel`.

Входы:

- `/cmd_vel_nav` — команда Nav2;
- `/cmd_vel_skill` — локальный навык прохождения препятствия;
- `/cmd_vel_teleop_test` — только для подготовительных тестов;
- судейский старт;
- `/robot_state`, `/imu`, `/odom` и диагностическое состояние датчиков;
- программный enable/disable и аварийный stop.

Выход:

- `/cmd_vel` типа `geometry_msgs/msg/Twist`.

Поведение:

- до подтверждённого сигнала старта всегда публиковать ноль или не владеть каналом согласно требованиям драйвера;
- выбирать ровно один источник команды по явному приоритету;
- ограничивать скорость и ускорение;
- собственный timeout свежести команды — не более 250 мс, при том что драйвер имеет watchdog 500 мс;
- при старом `/imu`, `/odom`, `/robot_state`, потере TF, критическом наклоне, ошибке робота или shutdown немедленно обнулить Twist;
- в `finally`, обработчиках `SIGINT/SIGTERM` и lifecycle deactivation несколько циклов послать нулевую команду;
- логировать входную команду, ограниченную команду, источник и причину остановки.

Начальный безопасный профиль для ровного пола:

```yaml
limits:
  vx_forward: 0.15
  vx_reverse: 0.08
  vy: 0.08
  wz: 0.30
  linear_accel: 0.20
  angular_accel: 0.50
  command_timeout_sec: 0.25
```

Пределы повышать только по журналам отдельных испытаний. Максимумы регламента хранить отдельно от рабочего профиля.

### 3. `go2_localization_bringup`

Запускает `slam_toolbox`, необходимые статические настройки и Nav2 поверх реальных `/scan`, `/odom`, `/imu` и TF. Не публикует дублирующий `odom -> base_link`, если это уже делает драйвер.

Для начала:

- remap выхода контроллера Nav2 с `/cmd_vel` на `/cmd_vel_nav`;
- сохранить `map -> odom` за SLAM;
- применять реальный footprint робота с небольшим, измеренным padding;
- не превращать все точки наклонной рампы в непреодолимую вертикальную стену;
- для Nav2 использовать 2D `/scan`, а `/point_cloud2` оставить для анализа рельефа и препятствий;
- проверить timestamp всех сообщений и не подменять их `now()`, если драйвер даёт корректное время.

### 4. `go2_mission_manager`

Lifecycle/state-machine узел. Состояния как минимум:

`BOOT -> WAIT_INTERFACES -> WAIT_START -> LOCALIZE -> NAVIGATE -> APPROACH_OBSTACLE -> EXECUTE_SKILL -> RECOVER/STOP -> FINISHED`.

На первом этапе реализовать только ровный пол и цель Nav2. Горки, качели, A-раму, мост и змейку добавлять отдельными навыками после подтверждения базовой локализации и управления.

### 5. Адаптация текущего веб-интерфейса

Веб-интерфейс должен читать ROS-карту, положение робота и изображение камеры, а цель передавать в `NavigateToPose`. Он не должен публиковать прямо в `/cmd_vel`. Ручное тестовое управление проходит через `/cmd_vel_teleop_test` и safety mux.

Это обязательная часть готового результата, а не дополнительная возможность. После запуска `flat_navigation.launch.py` оператор с Windows-компьютера должен открыть одну веб-страницу и увидеть:

- живую карту `/map`;
- положение и направление корпуса Go2 из TF;
- текущий путь Nav2 и поставленную цель;
- живое изображение `/camera/image_raw`;
- состояние соединения, SLAM, Nav2, датчиков, сигнала старта и safety mux;
- понятную причину, если движение заблокировано.

Управление мышью должно повторять текущую модель интерфейса:

1. короткий щелчок по свободной точке карты создаёт цель движения;
2. протягивание от точки задаёт положение и конечный yaw;
3. координаты пикселя преобразуются через `nav_msgs/msg/OccupancyGrid.info` в координаты рамы `map`, без ручного переворота осей;
4. сервер отправляет `nav2_msgs/action/NavigateToPose` в `/navigate_to_pose` и показывает accepted/rejected/executing/succeeded/canceled/aborted;
5. кнопка «Стоп» отменяет активную action-цель и блокирует команду через safety mux;
6. постановка цели запрещена, пока TF, карта, Nav2 или разрешение движения не готовы.

Веб-сервер слушает на интерфейсе Pi, доступном с операторского Windows-ПК, и печатает точный URL при запуске. Адрес и порт задаются параметрами. Нельзя требовать RViz для обычной постановки цели; RViz остаётся инструментом диагностики.

## Команды управления реальным Go2

Основная команда движения — только:

```text
/cmd_vel : geometry_msgs/msg/Twist
linear.x  = скорость вперёд/назад
linear.y  = боковая скорость влево/вправо
angular.z = угловая скорость вокруг вертикальной оси
```

Публиковать её с устойчивой частотой 20 Гц, пока движение разрешено. При отсутствии команды публиковать ноль. Частоту проверить на реальном драйвере.

Штатная MNN-политика Unitree сама переставляет ноги, поддерживает корпус и формирует походку. Программа команды задаёт скорость корпуса, маршрут и разрешённые параметры Sport API. Поэтому:

- не отправлять позиции, скорости или моменты 12 суставов;
- не использовать `/lowcmd`, `LowCmd`, прямой DDS `rt/api/sport/request` или WebRTC-команды;
- не воспроизводить Webots-анимацию суставов;
- не вызывать flip, jump, handstand и другие опасные команды;
- не менять FSM, высоту или gait без документированного разрешённого Sport-сервиса и проверки текущего состояния.

Разрешённый Sport-сервис применять только там, где обычного `/cmd_vel` недостаточно. Агент должен получить его точное имя и тип с судейского Pi. В коде сделать отдельный адаптер с allowlist команд, например `BalanceStand`, разрешённый gait и поза/высота в допустимом FSM. Если интерфейс или разрешение не подтверждены, функция остаётся выключенной.

## Датчики и их роль в алгоритме

- `/scan`: SLAM, глобальная и локальная costmap, аварийная проверка свободного коридора.
- `/point_cloud2`: высота, уклон, край платформы, геометрия рампы/качелей и различение проходимой поверхности от стены.
- `/camera/image_raw` + `/camera/camera_info`: визуальное распознавание препятствий и разметки; калибровку не подменять параметрами симулятора.
- `/imu`: наклон корпуса, вход/выход с рампы, скорость поворота, защита от опасного наклона.
- `/odom`: локальная скорость и короткие относительные перемещения; из-за дрейфа не использовать как абсолютную зачётную координату.
- `/robot_state`: режим, походка, высота, контакты стоп, температура, заряд и ошибки. Это источник разрешения/запрета навыка.
- `/tf`: единственный способ связывать измерения; ручные повороты облаков вне TF допустимы только как явно откалиброванный временный адаптер.

Для каждого сообщения проверять возраст, монотонность времени и соответствие `frame_id`. При несогласованном времени препятствие и поза будут «разъезжаться», что уже наблюдалось как наложение карт в симуляции.

## Первый набор испытаний

Испытания выполняются последовательно. Следующий уровень открывается только после сохранённого успешного отчёта предыдущего.

### A. Без движения

1. Все обязательные топики идут не менее 60 секунд.
2. TF-дерево связно, нет конфликтующих publishers.
3. Камера правильно ориентирована, CameraInfo соответствует изображению.
4. PointCloud2 отображается в RViz в раме `base_link` и совпадает с реальными объектами.
5. `/scan` видит стены, конусы, эстакады и качели на своей высоте среза.
6. Записывается rosbag всех обязательных топиков и TF.

### B. Проверка остановки

1. Нулевая команда не вызывает движения.
2. Удаление источника команды останавливает робота быстрее 500 мс; цель собственного mux — до 250 мс плюс задержка драйвера.
3. Завершение узла, `Ctrl+C`, исключение и потеря сенсора приводят к нулевой команде.

### C. Оси и ровный пол

1. Три малых импульса `+vx`, `+vy`, `+wz` подтверждают REP-103.
2. Движение вперёд на 1 м не превращается в дугу; оценить lateral drift и yaw drift.
3. Повороты `+30°` и `-30°` имеют правильный знак и сравнимую ошибку.
4. Квадрат или «вперёд–назад» выполняется на малой скорости без потери локализации.

### D. SLAM и цель

1. Карта не дублируется при повороте и возврате в исходную точку.
2. Цель прямо впереди приводит к положительному `vx`, а поворот вправо — к отрицательному `wz` по REP-103.
3. Nav2 останавливается перед настоящей стеной и прокладывает путь вокруг препятствия.
4. Низкие проходимые рампы анализируются 3D-модулем и не заменяются большим прямоугольным запретом.

### E. Препятствия

Только после A–D: ровный подход к горке, остановка перед ней, медленный подъём, вершина, спуск. Затем отдельно мост, качели, платформы и змейка. Каждый навык имеет собственные пределы скорости, условия входа, завершения и аварийного выхода.

## Логи каждого реального запуска

На каждый запуск сохранять один каталог с UTC-временем:

- параметры и git commit;
- список узлов/топиков/сервисов и их типов;
- rosbag: `/cmd_vel`, все входы mux, `/scan`, `/point_cloud2`, `/imu`, `/odom`, `/robot_state`, `/tf`, `/tf_static`, diagnostics, план и costmap;
- причины ограничения/остановки;
- фактические частоты и максимальный возраст сообщений;
- результат теста и измеренные ошибки;
- версия судейского образа/драйвера без копирования секретов.

Без такого каталога тест не считается подтверждённым.

## Критерий готовности первой версии

Первая версия готова к проверке на ровном полу, если одновременно выполнено следующее:

1. Фактический интерфейс Pi описан без предположений.
2. Read-only диагностика проходит 60 секунд.
3. Все оси проверены малыми импульсами и совпадают с REP-103.
4. Safety mux гарантированно обнуляет команду при timeout и завершении процесса.
5. Робот идёт по прямой к цели, корректно поворачивает в обе стороны и останавливается.
6. SLAM не рисует повторные повёрнутые копии карты.
7. Камера, `/scan` и `/point_cloud2` записываются и видимы в RViz/веб-интерфейсе.
8. Код не использует LowCmd, прямой WebRTC/DDS в обход драйвера, интернет во время заезда или внешние вычислители.
9. С Windows открывается веб-монитор; щелчок по карте создаёт `NavigateToPose`, цель отображается, робот едет к ней через Nav2 и safety mux, а «Стоп» отменяет цель и останавливает робота.

После этого можно начинать отдельную реализацию подъёма по горке. Успех Webots или кинематической демонстрации не засчитывается как подтверждение физического прохождения.

## Формат первого ответа агента

Агент не должен сразу переписывать весь проект. В первом ответе он обязан выдать:

1. найденные реальные топики, типы, QoS, частоты и frame IDs;
2. точный интерфейс Sport API и сигнала старта либо список того, чего ещё нет в доступе;
3. схему узлов и remap для перехода Webots -> real;
4. список файлов, которые он создаст или изменит;
5. команды read-only проверки;
6. отдельно обозначенный первый тест, при котором робот сможет двигаться, и все его ограничители;
7. перечень неподтверждённых предположений. Любое неподтверждённое поле должно оставаться конфигурацией `UNRESOLVED`, а не догадкой в коде.
