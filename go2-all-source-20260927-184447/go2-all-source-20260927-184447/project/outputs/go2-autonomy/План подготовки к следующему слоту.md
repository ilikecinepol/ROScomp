# Полностью автономная петля Go2: план разработки и следующего слота

Обновлено 25.09.2026. Это план работ, а не отчёт о готовой автономности.

## Цель и исходное состояние

Один бортовой процесс на Raspberry Pi 5 после стартового сигнала самостоятельно находит и проходит каждое требуемое препятствие один раз, выбирает порядок и возвращается к старту. ПК нужен для подготовки и наблюдения в тренировке; вычисления и решения зачётного заезда от него не зависят. Цель оптимизации — минимальное время полного зачётного круга, с учётом вероятности незачёта.

Есть ручные записи успешных прохождений, бортовой каркас, отдельные кнопки, загрузчик, диагностика и 220 прошедших программных тестов. Есть подтверждённый короткий ход вперёд. Нет подтверждённого автономного прохождения препятствий и готового аппаратного профиля.

Последний подготовленный пакет: training-6cdea568488dfb5df73c, пока только на ПК. На Pi последняя подтверждённая установленная версия — training-0a6a45137d51da752a48. Последняя попытка бокового теста не двигала робота: preflight отказал при 79 °C. Служба кабинета восстановлена. Последняя загрузка сорвалась по SSH timeout; слот закончен.

## Ответственность

- Разработка: архитектура, обработка записей, реализация, тесты, упаковка, загрузка, анализ причин отказа и настройка скоростей — агент.
- На полигоне: пользователь сообщает актуальный IP, подтверждает свободное место, наблюдает короткие тесты, сообщает фактический результат и при необходимости обращается к оператору площадки. Не должен редактировать код и искать файлы.
- До зачётного старта нужно уточнить у организатора официальный способ старта, критерии закрытия препятствия и возврата, доступность калибровок и точных времён датчиков. Сообщения организаторам без разрешения не отправлять.

## Что устанавливать

Базовый стек остаётся текущим: Python из окружения организатора, его go2.py/WebRTC, NumPy, SciPy и OpenCV без графического интерфейса. Headless-зависимости уже были установлены на Pi в team_wolf_setup/perception_deps. На ПК есть work/go2-perception/.venv. До обновления снять точные версии и собрать воспроизводимый список; не обновлять всё до последних версий перед слотом.

План установки: только проверенный пакет нашего приложения и действительно недостающие зависимости. При необходимости заранее скачать совместимые с ОС, архитектурой и Python Pi колёса. Не переносить Windows-окружение на Pi. Проверять импорт OpenCV на Pi, чтобы не повторить ошибку libGL.

ROS 2, Nav2, другой драйвер робота и нейросетевой детектор не являются обязательными для текущей архитектуры. Их установку не включать в критический путь без измеренной необходимости. Наличие Unitree SDK2 в открытом доступе не доказывает доступность его интерфейса на выданном Go2 Pro; рабочий интерфейс организатора сохраняем.

## Очередь разработки до слота

### 1. Воспроизводимый разбор данных

Проверить полноту скачанных сессий и создать индекс: препятствие, начало/конец попытки, профиль скорости, результат, комментарии, версия программы. Выделить удачные проходы, падения и остановки. Разделить данные для настройки и проверки по сессиям, чтобы не оценивать распознавание только на тех кадрах, по которым его подбирали.

Ручные записи — примеры геометрии и управления, а не готовые маршруты для слепого воспроизведения. Не объединять координаты разных запусков без привязки.

### 2. Адаптер датчиков и процедура калибровки

Исправить несовпадение требований старого профиля с реальными доступными полями. Для каждого подтверждения хранить способ измерения, исходный журнал, погрешность и условия применимости. Не заполнять verified=true ради зелёной кнопки.

- Координаты: короткие независимые проверки вперёд, вбок и поворота; сопоставить фактическое движение, одометрию, IMU и движение изображения. Проверить знак, масштаб, систему отсчёта и поведение после переподключения.
- Лидар: установить пригодный способ проверки возраста измерения. Сейчас содержимое меняется, stamp постоянен, cloud_scan_num постоянен; несжатый поток не ответил за 20 секунд. Нужен доступный точный источник времени либо отдельно обоснованная схема оценки задержки и свежести с обозначенной неопределённостью. Получение пакета не приравнивать к времени съёмки.
- Камера: найти калибровку именно выданной камеры и её разрешения. При отсутствии — подготовить процедуру измерения с разрешённым калибровочным объектом. До этого не переводить пиксели в метры по произвольному фокусному расстоянию.
- Идентификация: проверить доступный способ связать назначенные Pi и робота; одинаковая версия прошивки не является серийным номером.

Выход: мастер проверки в одном окне, конкретный список недостающих измерений и аппаратный профиль с прослеживаемыми доказательствами.

### 3. Локальная карта и распознавание

Сформировать карту опорных поверхностей, высоты, занятости и неизвестных областей. Учитывать корпус, запас на локализацию и края конструкций. Пустота в облаке не означает свободный пол.

- Змейка: объединять полосы одной стойки; сопоставлять изображения и вертикальные объекты лидара; выбирать согласованную группу стоек и порядок обхода; проверять свободные коридоры с обеих сторон.
- Горка: определить вход, ось ската, вершину, спуск и свободную площадку выхода.
- Качели: отличить их от неподвижного моста; учитывать изменение наклона доски по ходу прохода, а не идти по заранее неизменной плоскости.
- Рампа: выделить отдельные подъёмы, площадки, стыки и спуск; использовать успешную ручную запись как ориентир для настройки, не как доказательство универсальной скорости.
- Чужие роботы: отслеживать изменения занятости, ждать или перестраивать подход. Если объект не классифицирован, сохранять его как препятствие. Отдельно обрабатывать перекрытие самой конструкции.

Выход: просмотр записи с нанесёнными объектами, уверенностью, предполагаемым путём и причиной отказа. Ложное распознавание должно быть видно до команды движения.

### 4. Навыки и полная миссия

Для каждого навыка реализовать состояния: поиск → подход → выравнивание → вход → прохождение → выход → подтверждение. Определить наблюдаемые признаки завершения; таймер сам по себе не закрывает препятствие. Остановка и выход из ошибки должны работать независимо от обработки видео.

Исправить состав миссии: старый каркас использует пять типов с отдельным bridge. Для физической полосы пользователя требуются четыре — змейка, горка, качели, рампа. Список требуемых препятствий должен быть явным, согласованным с регламентом; контроллер не должен искать несуществующий пятый объект или засчитывать один дважды.

Общий планировщик оценивает стоимость переходов и время прохождения, выбирает порядок с учётом занятости. Хранит идентификаторы уже пройденных объектов и стартовую привязку. Возврат подтверждается позой и наблюдаемыми ориентирами с допуском из правил, а не только накопленной одометрией.

Разделить тренировочный запуск и зачётный: закрытие окна ПК может останавливать тренировку, но зачётная автономия после старта не должна зависеть от SSH, окна или внешних вычислений. Штатная аварийная остановка сохраняется. Официальный сигнал старта ещё нужно интегрировать.

### 5. Удобство и выпуск

Одна панель: IP из буфера, подключение/обновление, проверка датчиков, отдельные препятствия, вся петля, остановка, просмотр результатов, скачивание только новых файлов. Показывать этап и конкретную причину ожидания. Уже созданные рабочие инструменты записи и скачивания переиспользовать.

Исключить зависимость видео от переключения профиля скорости. Не перезапускать весь сеанс ради нового изображения. Очереди кадров ограничить; устаревшие кадры отбрасывать. Командный цикл и остановка не должны ждать видео, диска или скачивания.

Пакет: контрольные суммы, версии зависимостей, проверка перед установкой, предыдущая рабочая версия для отката. Не заменять исходник запущенного процесса и не убивать чужие сеансы управления.

## Проверки до живого запуска

Помимо существующих тестов: прерывание каждого потока, повтор и перестановка пакетов, скачок координат, зависание обработчика, ошибка записи, потеря SSH в тренировке, перезапуск Pi, объект поперёк маршрута, перекрытый выход и повторное обнаружение уже пройденного препятствия. Проверять фактическую команду остановки и её подтверждение.

На записанных сценах измерить задержку и ошибки распознавания. На Pi измерить время обработки и частоту команд; допустимую скорость выбирать с учётом задержки, торможения и доступного пространства. Программные тесты и воспроизведение записей не заменяют физического зачёта.

## Как добиваться скорости

Сначала добиться повторяемых полных прохождений. Затем отдельно уменьшать время подхода, выравнивания, движения по ровному полу, скатам и спуску. Начальная сетка скоростей — из реально наблюдённых проходов, а не максимум API. Менять по одному параметру и сравнивать несколько повторов при одинаковых условиях.

Для каждой версии сохранять: время полного круга и этапов, успешные попытки/общее число, падения, вмешательства, ожидания чужих роботов, задержку восприятия. Быстрый незачёт хуже более медленного полного круга. Победу нельзя обещать без результатов соперников и измерений на той же раскладке.

Температурные остановки остаются в коде: они не предмет оптимизации скорости. Последние 79 °C требуют проверки перед новыми движениями.

План не запускает фоновую работу и не означает, что перечисленные доработки уже выполнены. Следующее действие разработки: индекс записей и воспроизведение распознавания змейки с наложенным маршрутом; параллельно по смыслу подготовить процедуру измерения координат и времени, чтобы не сочинять её во время слота.
