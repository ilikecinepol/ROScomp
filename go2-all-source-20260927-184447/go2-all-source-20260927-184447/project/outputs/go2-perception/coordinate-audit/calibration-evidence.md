Строка 67 файла лидара — **закомментированный** вариант `baselink2lidar` с другими смещениями. Действующая строка внутри данного архивного файла — 68; комментарий нельзя выдавать за активное значение.

По названию `baselink2lidar` нельзя без реализации установить, описывает ли массив позу дочерней системы в родительской или активное преобразование координат точек в обратном направлении. Для `imu2lidar` комментарий задаёт порядок компонент, но не описывает порядок перемножения поворотов. Для массива `baselink2lidar` единицы и правила применения в той строке не написаны. Числа углов похожи на радианы, но этого недостаточно для построения подтверждённой матрицы. `2.88` не является найденным тангажом RGB-камеры.

Особенно существенно различие имён: `[0.28216, 0, -0.02467, 0, 2.88, 0]` фигурирует как корпус—лидар в одном модуле и `T_imu2lidar` в другом, тогда как самостоятельный `imu2lidar` в первом модуле равен `[0, 0, 0, π, 0, 0]`. Это требует проверки источника IMU и семантики каждого модуля, а не механического соединения массивов.

## RGB-камера: что не найдено

В проверенных конфигурациях нет применимой пары `K` и `D`, модели дисторсии, матриц `R/P`, значений `fx/fy/cx/cy`, FOV и преобразования камеры к `utlidar`, `base_link` или `odom`.

По описи архивный `rootfs/unitree/module/video_hub/` содержит исполняемый `videohub`, без соседнего читаемого файла калибровки. Бинарный код не разбирался. Определение `rootfs/unitree/module/programming_actuator/unitree_go/msg/dds_/_Go2FrontVideoData_.py:24–28` содержит только `time_frame`, `video720p`, `video360p`, `video180p`; внутренние параметры камеры и extrinsic там не передаются.

Найденный `utrack/config/ukd_fitting_3d_calib_params.yaml` содержит наборы матриц `n_matrix`, `n_matrix_p6`, `n_matrix_p18` и т. п. размером 36×3. В нём нет `K/D`, размеров RGB-кадра, фокусных расстояний и привязки к видеопотоку. Одно слово `calib` в имени не даёт оснований использовать эти данные для камеры. Назначение этого файла в рамках проверки не установлено.

## Практический вывод

На основании только этих материалов допустимо хранить RGB-вход рампы в пикселях и карту в её заявленной системе `odom`. **Переход от пикселей входа к метрам и курсу робота пока не подтверждён.** Подстановка архивного `baselink2lidar` не решает отсутствие калибровки камеры и может повторно применить уже учтённый поворот к готовой карте `odom`.

Для завершения цепочки нужны текущие параметры `K/D` для фактически получаемого режима видео, описание оптических осей и изменений кадра, подтверждённая цепочка камера—корпус—лидар, смысл позы `rt/utlidar/robot_pose` и согласованное время. При наличии текущих `camera_info`/TF или конфигов их следует связать с версией действующего драйвера и проверить проекцией видимых неподвижных поверхностей. Новые числовые значения калибровки в этом отчёте не придумывались.
