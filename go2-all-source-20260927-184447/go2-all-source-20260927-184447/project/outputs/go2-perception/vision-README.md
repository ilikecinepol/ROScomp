# Поиск видимой рампы на RGB-кадре

Модуль: `work/go2-perception/ramp_vision.py`. Это локальный исследовательский этап: он не подключается к роботу и не отправляет команды движения.

На сохранённых кадрах выделена серая поверхность рампы с тремя внутренними поперечинами. Зелёная нижняя граница — **предполагаемый вход в координатах изображения**. Стрелка обозначает ось изображения рампы. Она не задаёт поворот или скорость робота.

Алгоритм ищет длинные близкие к горизонтальным линии по всему изображению, объединяет короткие разрывы, проверяет семейство поперечин, обе боковые границы и тёмную малонасыщенную поверхность. Фиксированных координат рампы, рамок интереса или чтения контрольной разметки в детекторе нет. Одни только серый цвет или прямоугольная форма не достаточны.

## Результат API

`detect_ramp(image_bgr)` принимает массив NumPy `uint8`, BGR, H×W×3. Результат можно сериализовать в JSON:

- `candidates[].quadrilateral_px`: дальний левый, дальний правый, ближний правый, ближний левый углы;
- `entrance.endpoints_px` и `entrance.center_px`: предполагаемая нижняя граница и её середина;
- `direction.coordinate_frame = image_nonmetric`: направления только на изображении;
- `robot_bearing_deg` и `distance_m` равны `null`: калибровки и метрической привязки нет;
- `confidence_heuristic` — эвристическая согласованность обнаруженных признаков, **не вероятность правильного распознавания**;
- `evidence` и `diagnostics`: видимые признаки, причины отбрасывания и ограничения.

`render_overlay(frame, result)` возвращает размеченную копию кадра, не меняя оригинал. CLI принимает путь к кадру, `--output` для JSON и необязательный `--overlay` для картинки. Для работы нужны NumPy и OpenCV; они подготовлены в `work/go2-perception/.venv`.

## Что проверено

В `vision-validation.json` записаны результаты 13 локальных проверок: пять почти одинаковых кадров одной неподвижной сцены, горизонтальное отражение, увеличение и уменьшение яркости, перенос изображения, уменьшение разрешения, а также три отрицательных фрагмента — стена, мат и потолок.

На десяти положительных примерах найдено ровно по одному кандидату. Пересечение с приблизительной ручной разметкой IoU составляет 0,937–0,957; ошибка центра нижней границы — 2,5–6 пикселей, включая пример с половинным разрешением. На трёх отрицательных фрагментах кандидатов нет. Ручная разметка находится только в проверочном сценарии `vision-validation.py`, не в детекторе.

**Это проверка одной сцены, а не измерение точности на разных полигонах.** Отражение, перенос и изменение яркости не являются независимыми сценами. Детектор может пропустить гладкую рампу без поперечин, рампу при большом крене камеры, частично закрытую, ближнюю или обрезанную рампу. Другой похожий серый объект с планками может дать ложное обнаружение. Не измерены расстояние, уклон, проходимость и соответствие рампы точкам лидара. Сведения о них нельзя выводить из этого JSON.

Дополнительно проверены пять кадров новой записи `20260916T110043Z`, **без изменения модуля и его параметров**; совпадение SHA256 с первой проверкой контролирует сценарий `vision-fresh-validation.py`. На каждом найден ровно один кандидат; IoU относительно прежней приблизительной разметки — 0,955–0,960. Разметка `vision-fresh-camera_00.jpg` визуально проверена. Робот не перемещался: эта запись также не является независимой сценой или ракурсом. Результаты сохранены в `vision-fresh-validation.json`.

В этой короткой серии из пяти кадров средняя длительность одного вызова детектора на локальном Windows ПК — **113,8 мс**, максимум **124,0 мс**. Измерялся только `detect_ramp`, включая первый вызов; чтение файлов и рисование не учитывались. Это не измерение производительности Raspberry Pi и не гарантированная частота обработки видеопотока.

Для дальнейшей проверки нужны новые ракурсы и отрицательные сцены; для навигации — подтверждённая калибровка камеры, согласование времени и координат с лидаром и проверка пространства у входа.
