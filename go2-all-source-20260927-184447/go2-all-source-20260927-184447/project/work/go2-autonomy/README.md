# Go2: автономная миссия полуфинала

Пакет содержит программу миссии для пяти видов препятствий: горка (`aframe`), мост (`bridge`), качели (`teeter`), слалом (`slalom`) и платформы (`platforms`). Она выбирает порядок по наблюдаемой геометрии, проходит обязательные точки, проверяет выход и возвращается через наблюдаемую стартовую линию.

**Это ещё не подтверждённое полное решение для физического Go2.** Кинематические проверки проверяют логику программы на искусственных наблюдениях. Они не доказывают устойчивость, сцепление, возможность преодолеть конструкцию или правильность распознавания реальной арены. Пакет не содержит заранее записанного маршрута полигона.

## Что здесь уже есть

- Планирование подходов с учётом габаритов, неизвестных участков и подтверждённой опоры.
- Миссия для всех пяти видов, проверка каждого прохода и возврата через конечный отрезок стартовой линии.
- Отдельный отправитель команд: проверяет свежесть данных и команд, ограничивает скорость, запрашивает остановку при отказе.
- Запись решений, причин остановки и данных для повторного разбора.
- Обработка сохранённых облаков и изображений; локальные проверки ошибочных данных и отказов.

Для движения используется предоставленный Python/WebRTC-интерфейс `go2`: `Move` и `StopMove`. Перед движением проверяется режим `normal` или `mcf` (допуск mcf подтверждён пользователем 17.09.2026). Управление суставами и трюки в пакет не входят. ROS 2 для этого варианта не требуется.

Пределы предоставленного API: вперёд/назад до 0,6 м/с, вбок до 0,5 м/с, поворот до 1,0 рад/с. Настройки этого контроллера ниже. Они являются начальными ограничениями для испытаний, а не доказательством безопасной скорости на каждом препятствии.

## Что пока не готово для полного физического заезда

- Мост и качели по доступной верхней поверхности остаются неоднозначными. Сама форма настила не подтверждает наличие шарнира, опор или подвижность.
- Детектор реальной стартовой линии и её пересечения не завершён. Кинематическая сцена выдаёт идеальное наблюдение линии; это не заменяет реальный датчик.
- Нет подтверждённой калибровки действующей RGB-камеры и её связи с корпусом/лидаром. Пиксельный прямоугольник на изображении не превращается в расстояние или точку для движения.
- Требуют физических проверок локализация, временные шкалы, измерение опоры, реакция конкретного робота на движение и остановку, а также каждый навык преодоления.

Поэтому заполненный файл профиля сам по себе не делает полный заезд готовым. **Нельзя включать `validated_skills` или выставлять признаки подтверждения, чтобы обойти отсутствующие измерения и испытания.** Проверки синтетического мира используют отдельные искусственные данные; переносить их в профиль физического робота нельзя.

## С чего начать без робота

На текущем ПК можно открыть `test-offline.cmd`: он выполнит четыре кинематические проверки без подключения к собаке. Новые JSON-отчёты появятся в отдельной папке рядом. При переносе на другой ПК нужен Python 3.12+ с зависимостями пакета. План ближайшего тренировочного слота — в `NEXT_SLOT.md`.

Работайте из этой папки в отдельном Python-окружении. Для геометрии нужны NumPy и SciPy, для изображений — OpenCV. Окружение организатора используется отдельно при работе на бортовом компьютере.

Проверки запускаются так:

```text
python -m unittest discover -s tests -v
```

Кинематическая демонстрация — замкнутый цикл: программа выдаёт скорость, модель интегрирует движение, затем программа получает новое наблюдение. Поза не переносится прямо к очередной цели. Варианты сцены меняют перенос, поворот, начальное положение и задержку наблюдений. В них отсутствуют физика лап, качание, скольжение, контакт с конструкцией и ошибки реального распознавания.

В отчёте такой проверки всегда указано:

```text
scope = kinematic_not_physics_not_robot_validation
```

## Режимы запуска

Команды выполняются из папки пакета. `python` обозначает интерпретатор выбранного окружения; на Pi используйте окружение организатора. `robot-01` ниже — пример: замените его фактическим назначением робота.

```text
python -m wolf_go2 --help
python -m wolf_go2 demo --seed 0 --output demo-0.json
python -m wolf_go2 replay --capture recording --output replay-report.json
python -m wolf_go2 profile-template --robot-id robot-01 --output robot-01.json
```

`recording` — каталог ранее полученной записи. `demo` и `replay` сохраняют файл отчёта; режимы работы с живыми потоками создают новый каталог сессии. Для `observe` и `live` выбирайте ещё не существующий выходной каталог.

| Режим | Назначение | Соединение с роботом |
|---|---|---|
| `demo` | Кинематическая проверка на синтетических сценах | Нет |
| `replay` | Повторная обработка ранее записанных данных | Нет |
| `profile-template` | Создание незаполненного профиля назначенного робота | Нет |
| `observe` | Сбор и проверка живых датчиков | Только при явном `--connect`; без команд движения |
| `live` | Выполнение автономной миссии | Только при явном `--execute` и выполненных проверках допуска |

Повторная обработка записи не требует VPN, остановки служб или занятого соединения с роботом. Она не посылает движения. Работа с живыми потоками занимает единственное WebRTC-соединение: одновременно второй клиент запускать нельзя.

Следующие команды предназначены для назначенного Pi под Linux. `--sdk-dir` указывает каталог со штатным `go2.py`. Пример сбора датчиков на 45 секунд:

```sh
python -m wolf_go2 observe --connect --robot-id robot-01 --sdk-dir "$HOME/ai-robot" --output session-observe --duration 45
```

Для `observe` профиль необязателен: без него можно записать потоки, но нельзя подтвердить готовность геометрии и локализации. При наличии проверенного профиля добавьте `--profile robot-01.json`.

Команда подготовленного испытания после получения всех необходимых подтверждений:

```sh
python -m wolf_go2 live --execute --robot-id robot-01 --profile robot-01.json --sdk-dir "$HOME/ai-robot" --output session-live --duration 300 --start-file start-current.txt
```

Файл `start-current.txt` до запуска не должен существовать и должен находиться вне каталога журнала. В частности, нельзя указать в качестве сигнала создаваемый самой программой `session-live/start-token.txt`. Эта команда сначала открывает сеанс и ожидает сигнал текущей попытки. Она не устраняет перечисленные выше пробелы физического решения.

## Профиль назначенного робота

Один и тот же код можно запускать для разных назначенных роботов, но подтверждения должны относиться к конкретному экземпляру. Профиль хранит его идентификатор, ожидаемый уникальный серийный номер, проверенные системы координат, временные преобразования, ограничения и свидетельства испытаний.

Совпадение версии прошивки не отличает четырёх одинаковых роботов. При запуске должны совпасть назначение и фактическая идентичность устройства. Контракты времени относятся к монотонным часам конкретной загрузки Pi; после перезагрузки старое соответствие времени нельзя автоматически считать действительным.

Профиль не должен содержать координаты раскладки, маршрут, список обязательных точек или вручную назначенный тип видимой конструкции. Геометрия препятствий приходит из наблюдений. Пустые ячейки карты занятости не считаются подтверждённым свободным пространством.

## Как разрешается настоящий старт

Режим движения требует явного `--execute`, подходящего профиля и свежих проверенных потоков. Сам факт запуска программы не является сигналом начать движение.

Для старта используется подтверждение, связанное с текущей сессией: программа записывает случайный код `nonce` в `start-token.txt` внутри нового каталога сессии. Файл, указанный через `--start-file`, должен содержать именно этот код как обычный текст. Код действует только в текущем сеансе; прежний файл или код другого запуска не разрешает новую попытку.

После проверки готовности подготовленного опыта подтверждение создаётся копированием текущего кода. Для приведённого выше примера, из второго терминала в той же папке:

```sh
cp session-live/start-token.txt start-current.txt
```

Это локальный сигнал тренировочного запуска. Подключение к официальному судейскому сигналу старта должно быть реализовано отдельно.

Такое подтверждение допускает запуск подготовленного опыта; оно не подтверждает калибровку или пригодность неподтверждённого навыка. Перед испытанием должны быть выполнены реальные условия полигона и доступна физическая остановка.

## Как читать результат

Успех миссии требует пяти разных подтверждённых видов и фактического возвратного пересечения наблюдаемой стартовой линии. Достижение похожих координат, время ожидания или количество отправленных команд не заменяют эти события.

При отказе смотрите последнюю причину, свежесть потоков, сведения о локализации и ответ на `StopMove`. Запрошенная остановка и полученное подтверждение остановки — разные факты. Даже ответ API не заменяет проверку физического состояния при испытании.

Отчёт `demo` относится только к искусственному миру. Отчёт `replay` описывает обработку сохранённых измерений. Результат реального зачётного заезда устанавливают правила и судейство соревнования.

## Где искать код

| Файл | Назначение |
|---|---|
| `wolf_go2/models.py` | Контракты наблюдений, геометрии и решений |
| `wolf_go2/perception.py` | Наблюдения из облака и диагностические кандидаты изображения |
| `wolf_go2/mission.py` | Последовательность действий и подтверждение прохождения |
| `wolf_go2/navigation.py` | Проверка прохода с габаритами и планирование пути |
| `wolf_go2/sensors.py`, `consistency.py` | Проверки состояния, времени и согласованности данных |
| `wolf_go2/control.py` | Ограничение и отправка команд, остановка при отказе |
| `wolf_go2/profile.py` | Проверки профиля и его соответствия назначенному устройству |
| `wolf_go2/journal.py` | Запись данных с ограниченной очередью |
| `wolf_go2/simulation.py` | Отдельный искусственный мир для кинематических проверок |
| `tests/` | Локальные проверки логики и отказов |
